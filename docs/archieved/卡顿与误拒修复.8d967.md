# 卡顿与误拒修复

## 现状

实测发现三类问题会让用户在正常使用中"卡住"或"被劝退"，且都不是用户操作错误：

1. **静默挂起**：所有命令都在 `open_home` 后对 `$HOME` 目录做 `flock(LOCK_EX)` 且无超时。只要有任何进程持有 `$HOME` 的排他租约（同步盘、备份工具、其他 git-vws 长任务），命令就无限期阻塞且无任何输出。实测 `list` 被阻塞 8 秒以上无响应。
2. **全局串行**：该 `HOME` 锁在 `create` 的整个物化过程中持有。实测 2 万文件仓库 `create` 耗时 198 秒，期间该 `HOME` 下所有其他仓库的 `list` 也一起被阻塞 22 秒。
3. **误报与误拒**：
   - `remove` 用 `git fsck --unreachable` 判断私有对象是否可丢弃，但私有 `objects/info/alternates` 指向 authority，`fsck` 会把 **authority 里**的悬空对象（tag、notes、GC 未清的旧对象）算进私有闭包。实测一个只有 1 个 tag 的正常仓库，`create` 后立刻 `remove` 就被 `SESSION_DISCARD_RISK` 拒绝，唯一出路是 `--force`。
   - `doctor`/`gc` 把 authority 的 loose object 硬链接数 `nlink != 1` 判为 `RECOVERY_REQUIRED`。`git clone --bare` 本地克隆默认硬链接对象，实测该场景下 `doctor` 直接报 `DOCTOR_RECOVERY_REQUIRED`，`gc` 报 `GC_RECOVERY_REQUIRED`，且无法自行恢复。
   - `create` 未 `init` 时会先创建 `$HOME/.git-vws` 再报 `AUTHORITY_UNREGISTERED`，留下空状态根，此后 `doctor` 一直报 `DOCTOR_RECOVERY_REQUIRED`。
4. **提示无出路**：上述错误只给稳定 code，不说明下一步该做什么，用户只能猜或来问。

## 目标

- 任何命令都不再无限期静默阻塞：所有锁获取都有超时，超时给出可读错误。
- 只读路径（`list`/`doctor`/`gc` 的扫描）不再被写路径的长时间锁串行阻塞。
- `remove` 只判定**私有**对象闭包，不受 authority 悬空对象影响；已发布到目标分支的 session 可以直接 `remove`。
- `doctor`/`gc` 不再把本地 clone 的硬链接 authority 当作损坏；空状态根视为空仓库而非损坏。
- `create` 在未 `init` 时不再留下状态垃圾。
- 关键错误附带下一步操作指引。

## 修复后的实测结果

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| `$HOME` 被外部独占锁持有 | 无限期静默挂起 | 5 秒内返回 `STATE_BUSY` 并提示等待重试 |
| `create` 期间并发 `list` | 被阻塞 22 秒 | 0 秒返回 |
| `create` 全程持有 `$HOME` 锁 | 20.21 秒 | 0 秒（仅覆盖状态根提交的短临界区） |
| `git clone --bare` 本地克隆的 authority | `doctor` 报 `DOCTOR_RECOVERY_REQUIRED` | 正常，`recovery_required=false` |
| 正常仓库（含 tag/多分支）`create` 后 `remove` | `SESSION_DISCARD_RISK`，只能 `--force` | 直接成功 |
| 已 `publish` 的 session `remove` | `SESSION_DISCARD_RISK`，只能 `--force` | 直接成功 |
| 未 `init` 直接 `create` | 留下空状态根，此后 `doctor` 持续报 recovery | 不创建状态根，提示先 `init` |
| 有未发布提交或脏工作区时 `remove` | 拒绝 | 仍然拒绝（安全边界不变） |

## 空白 agent 试用发现并修复的问题

用三个完全空白的 agent 只带 CLI 真实试用，逐轮修复其暴露的问题：

| 轮次 | 发现的问题 | 修复 |
| --- | --- | --- |
| 一 | 仓库移动/删除后 registry 记录无法注销，`init` 报 `STATE_CORRUPT: foreign state record`，无任何出路 | 新增 `git vws forget`，可回收孤儿会话并注销陈旧记录（含设备号漂移） |
| 一 | `remove` 提示"先 publish"，但 `refs/notes/*` 等辅助 ref 的对象永远无法 publish，形成死循环 | 辅助 ref 与 authority 独有的私有对象不再阻断 remove；reflog 中已发布内容（按 patch-id 判定）也放行 |
| 一 | `TEMPLATE_UNSUPPORTED` 不说明是哪项 Git 配置 | 指出具体键、当前值、目标值与修复命令 |
| 一 | `list` 无法反映会话是否已发布，只能靠试 `remove` 探测 | `list` 新增 `removable` / `remove_blocker` / `worktree_path` 明文字段 |
| 二 | `PUBLISH_NON_FAST_FORWARD` 建议"在会话内 rebase"，但会话没有 remote，实际不可执行 | 错误与帮助直接给出 `remote add` / `fetch` / `rebase` 三条命令 |
| 二 | `AUTHORITY_IN_USE` 建议"用 gc"，但 gc 解决不了，真实解法是 remove 会话 | 改为明确提示先 remove 各会话 |
| 二 | `git vws --help` 被 Git 转交 man 而失败，且正确用法只写在 `-h` 里 | 帮助显式说明该差异；`init` 拒绝 `--repo` 并给出正确写法 |
| 二 | 未 init 就 create 会留下空状态根 | 先校验再创建；空状态根可由 `init` 重建 |
| 二 | 重复 init / 重复 create / remove 不存在会话的输出有歧义 | 分别给出"已注册未变更"、`Reused`、`ABSENT` 明确语义 |

## 性能与可读性（第二轮）

**性能**：定位到 `create` 慢的根因是逐文件 `fsync`——template 物化与 session COW 克隆都在每个文件后同步一次，`sample` 采样显示其占据绝大多数样本。改为**每个目录同步一次**（目录条目一次性持久化），并去掉目录创建时的冗余双同步、以及每文件重扫父目录的 O(n²) 查找。

| 场景（1 万文件） | 优化前 | 优化后 | 提升 |
| --- | --- | --- | --- |
| 首次 `create`（含 template 物化） | 106.6s | 6.3s | 17× |
| 复用 template 的 `create` | 48.0s | 4.0s | 12× |

持久性未削弱：骨架阶段对每个目录各同步一次，`cow_clone_inner` 仍同步根目录与父目录，`sync_tree` 对 Git 元数据保持逐文件同步。

**可读性**：`list`、`doctor`、`gc` 新增 `--human`，输出可读表格；不带该标志时 NDJSON 契约完全不变。

## man page（第三轮）

`git vws --help` 由 Git 转交 `man`，缺少页面时直接失败。新增 `git-vws man` 子命令，从 CLI 自身帮助文本生成 roff man page，安装后 `git vws --help` 正常工作：

    mkdir -p ~/.local/share/man/man1
    git-vws man > ~/.local/share/man/man1/git-vws.1

页面由帮助文本生成，不会与命令脱节；帮助中同时给出该安装步骤，`-h` 与直接调用二进制始终可用。

## 空白 agent 最终验收后补修（第四轮）

| 反馈 | 修复 |
| --- | --- |
| `git vws --help` 在无 man page 时只报 `No manual entry`，修法藏在读不到的帮助里 | 新增 `git-vws man --install` 一键部署；帮助与文档改为该命令 |
| `doctor` 提示"解码 path_hex 拿路径"，但解码出来是记录文件名 | `path_hex` 改为输出记录中的真实仓库路径；`--human` 直接打印可复制的 `forget` / `init` 命令 |
| 会话不继承 authority 的 `user.name`/`user.email`，首次 commit 即失败且帮助未提 | 帮助新增说明与两条 `git config` 命令 |
| 在会话 worktree 内运行 `git vws` 报 `AUTHORITY_NOT_SOLE`，帮助未提 | 帮助明确要求在会话外运行 |
| 帮助写 `STATE_BUSY`，实际会话锁是 `SESSION_BUSY` | 两个码都写明 |
| `remove -h` 让人以为"publish 后就能删"，实际工作区脏仍拦截 | 说明两个 blocker 独立，需各自解决 |
| `remove` 成功只输出 NDJSON | `remove --human` 输出可读结果 |
| `publish` 无改动仍报 published | 已同步时输出 `nothing to publish` |

`init` 重复执行保持返回 `AUTHORITY_DUPLICATE`（非零）：并发 init 的互斥契约依赖它，放宽会破坏既有并发安全测试。

## 影响范围

- 基础设施：`src/authority.rs`（HOME/状态根锁、空状态根、错误文案）、`src/git.rs`（错误文案通道）。
- 业务核心：`src/session.rs`（`remove` 的丢弃判定、census 的 authority 分类、`create` 前置校验）、`src/template.rs`、`src/cache.rs`（锁超时）。
- 入口面：`src/main.rs`（帮助与错误呈现）、`docs/zh`、`docs/en`、`README.md`。
- 不涉及：Git 对象格式、session 拓扑、publish 的 CAS 语义、COW 存储路径、checkpoint 协议。

## 架构示意

```text
命令入口
  ├─ 只读扫描（list/doctor/gc census）── 共享租约，不阻塞
  └─ 写事务（init/create/remove/publish/cache）
        └─ HOME 租约：仅覆盖状态根提交的短临界区，带超时
```
